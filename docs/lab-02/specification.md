# Lab 2 Sprint Engineering Specification

## 1. Sprint Goal

Deliver a Requester-facing ticketing MVP for TokTickIT: a Requester can select a
Development Requester identity, create an IT support ticket with attachments, receive an
official Ticket Number, and locate, inspect, and manage their own tickets and attachments —
all behind ownership checks and a consistent Zen Green UI — without any real authentication,
IT Staff workflow, or ticket-lifecycle logic beyond creation.

## 2. Stakeholder Request Interpretation

IT is ready to accept real tickets. Requesters need a professional, responsive flow to
describe a problem, classify it, attach evidence, and submit it. After submission they need
to find that ticket again, search/filter/sort their own list, open a detail view, and manage
attachments — all while one Requester is strictly prevented from seeing another Requester's
data. Because real login isn't built yet, a temporary "Development Requester Selector" stands
in for authentication so multi-user ownership can be exercised and tested now.

## 3. Scope

### Included
- Development Requester Selection screen (testing-only identity switch)
- Create Ticket (form, validation, attachment upload, Ticket Number generation)
- My Tickets (search, filter, sort, pagination, list/card views)
- Requester Ticket Detail (read-only ticket info + attachment management)
- Attachment lifecycle: add, download, soft-remove
- Ownership enforcement on every Requester-scoped read/write
- Zen Green Theme and reusable form/list/badge/state components
- Responsive behavior at desktop / tablet / mobile breakpoints

### Excluded
- Authentication: login, logout, passwords, sessions, tokens, real authorization
- IT Staff dashboard, queue, ticket claiming/reassignment, IT Priority changes
- Public Comments, Internal Notes, Actions Taken
- Any ticket status transition beyond the initial `NEW` status
- Administrator functions (managing users, roles, reference data)

## 4. Functional Requirements

- **FR-01** The system shall allow selecting one active Development Requester as the current
  testing identity before any ticket screen is accessible.
- **FR-02** The system shall allow changing the selected Development Requester at any time via
  a "Change Requester" action, reloading all Requester-scoped data.
- **FR-03** The system shall let the selected Requester create a ticket with Category, Related
  System, Summary, Description, and Requested Priority.
- **FR-04** The system shall let the Requester attach 0–5 supporting files during ticket
  creation.
- **FR-05** The system shall generate a unique, backend-issued Ticket Number on successful
  creation and display it to the Requester.
- **FR-06** The system shall persist a created ticket with `NEW` status and the creating
  Requester's ID.
- **FR-07** The system shall let the Requester view a paginated list of only their own tickets
  in My Tickets.
- **FR-08** The system shall let the Requester search My Tickets by Ticket Number or Summary.
- **FR-09** The system shall let the Requester filter My Tickets by Category, Requested
  Priority, IT Priority, and Current Status.
- **FR-10** The system shall let the Requester sort My Tickets by at least Created Date, Last
  Updated, and Ticket Number.
- **FR-11** The system shall page through My Tickets results with a defined default and
  maximum page size.
- **FR-12** The system shall let the Requester open a Ticket Detail screen for a ticket they
  own.
- **FR-13** The system shall reject a request for Ticket Detail (or any ticket sub-resource)
  belonging to a different Requester.
- **FR-14** The system shall display all ticket fields as read-only on Ticket Detail.
- **FR-15** The system shall let the Requester add a permitted attachment to an existing owned
  ticket, subject to the 5-active-attachment limit.
- **FR-16** The system shall let the Requester download an active attachment they own.
- **FR-17** The system shall let the Requester soft-remove an attachment they own, with a
  required removal reason.
- **FR-18** The system shall retain removed-attachment metadata visibly but block its download
  or preview.
- **FR-19** The system shall show loading, empty, no-results, and error states on every
  Requester-scoped screen.
- **FR-20** The system shall preserve entered form values when a submission fails due to a
  network/server error (not validation).

## 5. Business Rules

| ID | Rule |
|---|---|
| BR-01 | The official Ticket Number is generated by the backend and must be unique (format `TKT-YYYY-NNNNNN`, zero-padded, sequential per year). |
| BR-02 | A new Ticket begins with Current Status `NEW`. IT Priority is unset (`null`) until IT Staff acts in a later lab. |
| BR-03 | Lab 2 uses a Development Requester selector instead of login. The selected identity is for testing only and is not authentication; it must be visually labeled as such. |
| BR-04 | Only active Requesters (`isActive = true`) are shown in the Development Requester selector. |
| BR-05 | An inactive Requester cannot be selected, and if a stored session references one that later becomes inactive, the app forces re-selection. |
| BR-06 | Switching the selected Requester immediately invalidates and reloads all previously fetched ticket data. |
| BR-07 | A Ticket's `requesterId` is set once at creation from the currently selected Requester and cannot be changed by the Requester. |
| BR-08 | A Requester may only read or modify Tickets and Attachments where `ticket.requesterId` equals the selected Requester's ID; all other access returns 404 (not 403), to avoid confirming existence of another Requester's ticket. |
| BR-09 | Ticket Summary is required, trimmed, and must be 5–120 characters after trimming. |
| BR-10 | Ticket Description is required, trimmed, and must be 10–2000 characters after trimming. |
| BR-11 | Category and Related System are required and must reference existing, active reference rows. |
| BR-12 | Requested Priority is required and must be one of `LOW`, `MEDIUM`, `HIGH`. |
| BR-13 | Ticket Date, Ticket Number, Current Status, Ticket Owner, and IT Priority are system-generated/read-only and are never accepted from client input. |
| BR-14 | The Create Ticket submit action is disabled while a request is in flight, preventing duplicate-submission from repeated clicks. |
| BR-15 | If ticket creation fails due to a server/network error, no partial Ticket row is committed, and all entered form values (including selected attachments) remain in the form for retry. |
| BR-16 | If a Ticket is created successfully but one or more attachment uploads fail, the Ticket is still saved; the Requester is shown which files failed and may retry adding them from Ticket Detail. |
| BR-17 | Allowed attachment types are JPG, JPEG, PNG, WEBP, and PDF, validated by both extension and MIME type. |
| BR-18 | Maximum attachment size is 5 MB per file; oversized files are rejected client-side before upload and re-validated server-side. |
| BR-19 | A Ticket may have at most 5 **active** (non-removed) attachments at any time; removed attachments do not count toward the limit. |
| BR-20 | Attachment removal is a soft removal: the row is flagged `removedAt`/`removalReason`, the file remains addressable internally, but download/preview endpoints return 410 Gone for removed attachments. |
| BR-21 | A removal reason is required (5–200 characters) and stored with the removed attachment. |
| BR-22 | Only the owning Requester may add or remove an attachment; ownership is enforced against the parent Ticket, not the Attachment row alone. |
| BR-23 | Uploaded files are stored under a generated, non-guessable filename; the original filename is preserved only as metadata for display. |
| BR-24 | My Tickets search matches Ticket Number (exact/partial) or Summary (case-insensitive, partial). |
| BR-25 | My Tickets default sort is Created Date descending (newest first); ties break by Ticket Number descending. |
| BR-26 | My Tickets default page size is 10; permitted page sizes are 10, 20, 50; invalid page/pageSize values fall back to the defaults rather than erroring. |
| BR-27 | An empty state (no tickets exist yet) is visually distinct from a no-results state (filters/search matched nothing). |
| BR-28 | If the active-Requester list fails to load or is empty, the Development Requester Selection screen shows a safe error/empty state and blocks entry to ticket screens. |
| BR-29 | All Development Requester, ownership, and "session" state in Lab 2 is client-side only (e.g., in-memory/local state) and must be replaced by server-verified authentication in Lab 3; no security guarantee is implied by BR-03–BR-08 beyond convenience testing.

## 6. UI Specification Summary

Full detail lives in `ui-spec.md`. Summary:

- **Application shell**: TokTickIT wordmark, My Tickets / Create Ticket nav, current
  Requester name + Change Requester action, responsive hamburger nav on mobile.
- **Development Requester Selection**: single-purpose screen, dropdown of active
  Requesters only, explicit "testing only, not login" messaging, loading/empty/error states.
- **Create Ticket**: system-generated fields visually distinct (read-only styling) from
  editable fields; Summary/Description given generous width; Attachments section below main
  fields; primary Submit + secondary Cancel at the bottom; inline field-level validation;
  busy-state Submit button; success panel showing the generated Ticket Number.
- **My Tickets**: search bar, filter row (Category / Requested Priority / IT Priority /
  Status), sortable columns, pagination footer, Create Ticket action, badge styling for
  priority/status, responsive card layout under 768px.
- **Ticket Detail**: read-only header/info grid, Attachments panel (active + removed,
  clearly separated), Back to My Tickets navigation, no comments/notes/actions UI.
- **States**: every screen defines loading, empty, no-results (where applicable), and error
  presentations; none rely on color alone.

## 7. Data Changes

Prisma models added/extended (see `server/prisma/schema.prisma`):

- **Category** *(exists from Lab 1)* — add `isActive Boolean @default(true)`.
- **RelatedSystem** — `id`, `name @unique`, `isActive`, `createdAt`.
- **Requester** — `id`, `name`, `email @unique`, `isActive`, `createdAt`. (Named `Requester`,
  not `User`, to avoid implying real auth per BR-03/BR-29.)
- **Ticket** — `id`, `ticketNumber @unique`, `requesterId → Requester`, `categoryId →
  Category`, `relatedSystemId → RelatedSystem`, `summary`, `description`,
  `requestedPriority (enum: LOW/MEDIUM/HIGH)`, `itPriority (enum, nullable)`, `status (enum,
  default NEW)`, `ticketOwnerId (nullable, for future IT Staff use)`, `createdAt`,
  `updatedAt`.
- **Attachment** — `id`, `ticketId → Ticket`, `originalFilename`, `storedFilename @unique`,
  `mimeType`, `sizeBytes`, `uploadedAt`, `removedAt (nullable)`, `removalReason (nullable)`.

Indexes/constraints:
- `Ticket.ticketNumber` unique index (BR-01).
- `Ticket.requesterId` indexed (ownership filtering on every list/detail query).
- `Ticket(status, requestedPriority)` composite index to support filter+sort.
- `Requester.email` unique; `Requester.isActive` indexed (selector query).
- `Attachment.ticketId` indexed; `Attachment.removedAt` used as the soft-removal flag
  (non-null = removed) rather than a separate boolean, to also capture removal timestamp.

Migration decision: extend the existing single `init` migration lineage with a new
`add-ticketing-core` migration rather than editing the Lab 1 migration, per Prisma's
append-only migration history practice.

## 8. API Contract

Full request/response shapes live in `api-spec.md`. Endpoints:

- `GET /api/categories` — active categories
- `GET /api/related-systems` — active related systems
- `GET /api/requesters` — active Development Requesters
- `POST /api/tickets` — create a ticket (+ optional attachments)
- `GET /api/tickets` — selected Requester's paginated, searchable, filterable, sortable tickets
- `GET /api/tickets/:id` — one owned ticket with active + removed attachment metadata
- `POST /api/tickets/:id/attachments` — add an attachment to an owned ticket
- `GET /api/attachments/:id` — attachment metadata
- `GET /api/attachments/:id/download` — download an active attachment
- `PATCH /api/attachments/:id/remove` — soft-remove an owned attachment

Every endpoint that reads/writes a Ticket or Attachment requires an `x-requester-id` header
(the Lab 2 stand-in for auth) and enforces ownership server-side, returning `404` when the
resource doesn't belong to that Requester.

## 9. Acceptance Criteria

- **AC-01** Given valid Ticket data, when the Requester submits the form, then one Ticket is
  saved and the official Ticket Number is displayed.
- **AC-02** Given no Development Requester is selected, when the user attempts to open My
  Tickets, then the Requester Selection screen is shown.
- **AC-03** Given Requester B is selected, when a Ticket belonging to Requester A is
  requested, then the Ticket data is not returned (404).
- **AC-04** Given Summary is empty, when the Requester attempts to submit, then a field-level
  message appears and no API call is made.
- **AC-05** Given a valid ticket and viewport from mobile to desktop, when the Requester
  completes the create flow, then the confirmation shows the generated Ticket Number at every
  breakpoint.
- **AC-06** Given a 6 MB file, when the Requester selects it as an attachment, then it is
  rejected client-side with a size-limit message and not uploaded.
- **AC-07** Given a `.docx` file, when the Requester selects it as an attachment, then it is
  rejected with an unsupported-file-type message.
- **AC-08** Given a Ticket already has 5 active attachments, when the Requester tries to add
  another, then the addition is rejected with a limit-reached message.
- **AC-09** Given the backend is unreachable, when the Requester submits Create Ticket, then a
  safe error state is shown and all entered field values remain populated.
- **AC-10** Given Requester A has tickets and Requester B is then selected, when My Tickets
  loads, then only Requester B's tickets are shown and Requester A's tickets are absent.
- **AC-11** Given a search term matching no ticket, when the Requester searches, then a
  no-results state (not the empty state) is shown.
- **AC-12** Given a Requester with zero tickets, when My Tickets loads, then the empty state
  (not no-results) is shown.
- **AC-13** Given multiple pages of results, when the Requester changes page, then the correct
  page of the Requester's own tickets loads and pagination controls reflect the current page.
- **AC-14** Given an owned Ticket, when the Requester opens Ticket Detail, then all fields
  render as read-only with no editable controls.
- **AC-15** Given an owned Ticket with an active attachment, when the Requester clicks
  download, then the file downloads successfully.
- **AC-16** Given an owned active attachment, when the Requester soft-removes it without
  entering a reason, then the removal is blocked with a validation message.
- **AC-17** Given an owned active attachment, when the Requester soft-removes it with a valid
  reason, then it appears in the Removed section and its download control is disabled.
- **AC-18** Given a removed attachment, when a download is attempted directly via its API
  endpoint, then the server returns 410 Gone.
- **AC-19** Given an inactive Requester exists, when the Development Requester Selection
  screen loads, then that Requester does not appear in the dropdown.
- **AC-20** Given the active-Requester API call fails, when the Selection screen loads, then a
  safe error state is shown instead of a blank or crashed screen.
- **AC-21** Given the Requester changes their selected identity, when they navigate to My
  Tickets, then the ticket list reloads for the newly selected Requester.
- **AC-22** Given a desktop, tablet, and mobile viewport, when any Lab 2 screen is rendered,
  then no label is clipped, no message overlaps another element, and no unintended horizontal
  scroll occurs.
- **AC-23** Given the Requester is using only a keyboard, when they operate the Create Ticket
  form, then every control is reachable and operable with a visible focus indicator.
- **AC-24** Given a Requester attempts to fetch another Requester's Ticket Detail by editing
  the ticket ID directly, then the response is 404 and no ticket data renders.
- **AC-25** Given the Requester submits a valid Create Ticket form, when the request is in
  flight, then the Submit button shows a busy state and is disabled against repeat clicks.

## 11. Assumptions and Decisions

- **Ownership failures return 404, not 403** — prevents confirming that a ticket ID exists
  under another Requester's ownership (information-disclosure minimization), consistent with
  BR-08.
- **Ticket Number format** `TKT-YYYY-NNNNNN`, generated in a single DB transaction with the
  ticket insert to guarantee uniqueness under concurrent submissions.
- **`x-requester-id` header** is used as the Lab 2 stand-in for an auth token so the API shape
  will resemble Lab 3's real `Authorization` header and require minimal rework.
- **Soft removal uses a nullable `removedAt` timestamp** rather than a boolean flag, so the
  removal time is captured without an extra column.
- **Attachment storage** uses local disk under `server/uploads/` with a generated UUID
  filename; a real object-store migration is deferred beyond Lab 2 scope.
