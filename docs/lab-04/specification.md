# Lab 4 Specification

## 1. Sprint Goal

Deliver Lab 4 as the operational closure of the TokTickIT ticket lifecycle: IT Staff record structured **Actions Taken** on any ticket, a server-enforced **resolution gate** blocks premature `→ Resolved` transitions while follow-up work is still pending (completing the rule deferred by Lab 3 BR-15), and Requester and IT Staff **dashboards** give each role an at-a-glance, drill-down-backed view of their work — all without regressing Labs 1–3, and hardened for accessibility, failure safety, and concurrency correctness.

## 2. Stakeholder Request

Lab 3 deferred one load-bearing rule: *"Lab 3 has no Actions Taken rule; resolution blocking based on incomplete Actions Taken is deferred to Lab 4"* (Lab 3 specification, BR-15). Stakeholders now ask for that rule to become real and auditable: every significant thing IT does on a ticket must be recorded as a structured Actions Taken entry (what was done, what resulted, whether follow-up is still required); a ticket with unresolved follow-up **cannot** be marked Resolved no matter which button the UI shows; and both Requesters ("what needs me?") and IT Staff ("what needs us?") get simple dashboards that answer that question in one glance and link straight into the queues they already know. This specification is the engineering contract every other Lab 4 branch builds on — it resolves every judgment call (edit policy, gate shape, concurrency mechanism, metric definitions, timezone rule) so implementation branches never have to guess.

## 3. Scope

### 3.1 Included

- Actions Taken CRUD (create + controlled update) on staff tickets, with a documented shape, validation rules, authorship rule, and edit policy.
- The resolution gate: a server-side precondition on the `→ Resolved` edges of the Lab 3 transition matrix.
- The complete 8-state transition matrix with the gate applied (matrix shape unchanged from Lab 3).
- Requester dashboard (`GET /api/dashboard/requester`) and IT Staff dashboard (`GET /api/dashboard/staff`, reused by Administrator).
- Optimistic-concurrency (`expectedUpdatedAt` → `409`) on Ticket status/owner/priority writes and Actions Taken edits.
- Requester read-only visibility of Actions Taken on their own tickets.
- Full Labs 1–3 regression (auth, Requester ticket/attachment flows, staff queue/detail, comments, notes, admin user management) still green and unmodified.
- Final hardening: accessibility, zero console errors, no dead UI, duplicate-click/retry safety, data-preserving failure recovery.

### 3.2 Explicitly Excluded

Baseline is handout §4.2; Lab 4 adds no:

- SLA clocks, timers, escalation rules, or due-date computation.
- Notifications (email, in-app, or otherwise).
- Inventory, asset, or billing linkage.
- Multi-level approval workflows.
- BI tools, exports, or analytics beyond the dashboard cards defined in §5/BR-08.

- Changes to the 8-state enum itself or the matrix shape (only a precondition is added).

## 4. Functional Requirements

- **FR-01 Actions Taken create:** Authenticated active IT Staff and active Administrators can create an Actions Taken entry on any ticket (assigned or unassigned — ownership ≠ authorship, BR-06). Requesters cannot create.
- **FR-02 Actions Taken read:** IT Staff and Administrators can list a ticket's Actions Taken in chronological order. Requesters can list Actions Taken on their **own** tickets read-only (no create/edit controls rendered or honored).
- **FR-03 Actions Taken update:** The original author (while still active IT Staff) or any active Administrator can edit an entry's correctable fields (BR-06). Any active IT Staff or Administrator can explicitly resolve any entry's pending follow-up (BR-07). All edits carry an optimistic-concurrency check (BR-09).
- **FR-04 Resolution gate:** The server blocks `OPEN → RESOLVED`, `IN_PROGRESS → RESOLVED`, and `WAITING_FOR_REQUESTER → RESOLVED` while the ticket has at least one unresolved follow-up (BR-07). The block returns a distinct `409 RESOLUTION_BLOCKED` error, not the generic disallowed-transition error.
- **FR-05 Transition matrix with gate:** The Lab 3 8-state matrix is unchanged in shape; the gate is a precondition applied to exactly the three `→ Resolved` edges above. All other edges behave exactly as in Lab 3.
- **FR-06 Requester dashboard:** An authenticated Requester gets aggregate cards over their own tickets with exact queries (BR-08), empty states, and drill-down links into My Tickets.
- **FR-07 IT Staff dashboard:** Authenticated active IT Staff get aggregate cards over the shared queue with exact queries (BR-08), empty states, and drill-down links into the staff queue. Active Administrators reuse the same endpoint in read-only aggregate form (no queue/detail permission implied beyond Lab 3).
- **FR-08 Concurrency safety:** Ticket status/assignment/priority writes and Actions Taken edits accept an `expectedUpdatedAt` precondition and return `409 VERSION_CONFLICT` (with current `updatedAt`) on staleness (BR-09). The UI surfaces the conflict and preserves user input.
- **FR-09 Labs 1–3 regression:** Every Lab 1–3 flow (authentication incl. `mustChangePassword`, Requester ticket/attachment flows on session identity, staff queue/detail, Public Comments, Internal Notes, admin user management, `problemAppearsResolvedAt` signaling) continues to pass unmodified.
- **FR-10 Hardening:** All Lab 4 screens meet the accessibility rules (keyboard, labels, focus, `aria-describedby`, badge text), produce no console errors, contain no dead UI (every button/link resolves to a working action or a documented disabled state with reason), disable during in-flight requests with retry safety (no duplicate creates on double-click), and preserve entered data across network/server failures with an explicit Retry path.

## 5. Business Rules

1. **BR-01 Action Date/Time is server-set.** `actionDate` is assigned by the server as `getNow()` (the BR-14 injectable app-code clock, never the Postgres clock) at creation and is never accepted from the client. Implementations MUST pass `actionDate: getNow()` explicitly on insert and MUST NOT rely on the Prisma `@default(now())` DB default (which fake timers cannot freeze). If the create body (or any edit body) contains `actionDate`, `performedById`, `followUpResolvedAt`, or `followUpResolvedById` — any value, including `null` — the server rejects with `400 VALIDATION_ERROR` (strict rejection, never silent ignore). Rationale: matches the `createdAt` pattern of `PublicComment`/`InternalNote`, prevents backdating/forward-dating, and keeps dashboard "today/recent" queries on a single trustworthy clock. Strict rejection (not ignore) forces clients to stop sending server-owned fields and is trivially testable. The immutable `actionDate` doubles as the display timestamp; `updatedAt` records later corrections (BR-06).
2. **BR-02 Action Description is required and bounded.** Required, trimmed, length 5–2,000 characters (after trim). Empty/whitespace-only or >2,000 chars → `400 VALIDATION_ERROR`. The 2,000-char ceiling matches comments/notes so the same UI counter conventions apply; the 5-char floor rejects junk single-character rows while staying testable.
3. **BR-03 Result is a required controlled vocabulary.** `result` is required and must be exactly one of `RESOLVED_STEP | WORKAROUND | INFO_REQUESTED | ESCALATED | NO_FURTHER_ACTION` (wire values uppercase with underscores; UI labels title-cased). Free-text narrative belongs in `description`. Rationale: a controlled vocabulary is queryable (dashboards and tests can count "how many escalations"), prevents vague prose from becoming the de-facto status, and keeps validation to a single enum check. Unknown values → `400`.
4. **BR-04 Performed-by is always the authenticated actor.** `performedById` is derived server-side from the session user and never accepted from the client (mirrors Lab 3 BR-03's identity rule; client-supplied `performedById` → `400 VALIDATION_ERROR` per BR-01, never honored). The response embeds a safe author shape `{ id, name, role }`; hashes are never exposed.
5. **BR-05 Follow-Up Required + Follow-up Note + Attachment Notes.**
    - `followUpRequired` is a required boolean, default `false` when omitted on create.
    - `followUpNote`: **required (trimmed, 5–1,000 chars) when `followUpRequired = true`; prohibited when `followUpRequired = false`.** If `followUpRequired = false` and a non-empty `followUpNote` is supplied, the server rejects with `400 VALIDATION_ERROR` (strict rejection, **not** silent ignore). Rationale: silent-ignore drops user intent without feedback and creates "I typed a note and it vanished" bugs; strict rejection forces the client to make the intent explicit and is trivially testable in both directions.
    - `attachmentNotes` is an **optional free-text pointer** (trimmed, max 500 chars) naming/describing a file already attached through the Lab 2 attachment flow (e.g. `"screenshot FW-log-2026-10-01.png"`). It creates no upload path, stores no bytes, and never references a path outside the ticket's existing attachments. Lab 4 adds no file-upload scope.
    - **Resolved-row history exemption (normative):** once a row is resolved (`followUpResolvedAt IS NOT NULL`), its stored `followUpNote` is retained verbatim for audit even if `followUpRequired` later becomes `false` (see BR-06 transitions T2). The BR-05 prohibited check applies to **client-supplied** `followUpNote` values only: with `followUpRequired = false` the client MUST omit `followUpNote` or send `null`/empty (any non-empty supplied value → `400`); the server never clears the stored note as a side effect of flipping the flag. Without this exemption, clearing the flag would erase the history of why follow-up was needed.
6. **BR-06 Authorship and edit policy (ownership ≠ authorship).**
    - **Create:** any **active** IT Staff member or any active Administrator may create an Actions Taken entry on **any** ticket, whether assigned, unassigned, or owned by someone else. The handout states an Action Taken *"may be by a different IT Staff member"* — this rule adopts that sentence literally. Ticket ownership is never a precondition for authoring. Requesters cannot create (server `403`; the Requester UI renders no create/edit controls).
    - **Edit (correctable fields):** an entry, once created, **can** be edited — Lab 4 is **not** strictly append-only (the handout says "create and update", and operational records legitimately need correction, unlike the conversational record of comments/notes). Editable: `description`, `result`, `followUpRequired`, `followUpNote`, `attachmentNotes`. Immutable: `id`, `ticketId`, `performedById`, `actionDate`. Server-owned `followUpResolvedAt`/`followUpResolvedById` are never client-settable (BR-01: supplied → `400`). Every edit bumps `updatedAt` and honors the concurrency precondition (BR-09).
    - **Who may edit correctable fields:** only the **original author while still active IT Staff**, or **any active Administrator**. Other IT Staff (including the Ticket Owner) must add a **new** entry rather than rewriting a colleague's record. Rationale: preserves accountability in a shared queue without freezing legitimate corrections; administrators retain a correction path for deactivated-author rows.
    - **Follow-up resolution is the exception:** **any** active IT Staff or active Administrator may resolve **any** entry's pending follow-up via the explicit resolve operation (BR-07), because follow-up work is routinely completed by a different staffer than the one who flagged it.
    - **PATCH evaluation order (normative; stored row S vs merged row M):** for `PATCH …/actions-taken/:actionId`, let S be the stored row and M be S with the request's correctable fields applied. **Merge rule:** each own-property correctable key present in the parsed JSON body overwrites S (`key in body` after JSON parsing — keys dropped by JSON serialization such as `undefined` count as absent); for nullable keys (`followUpNote`, `attachmentNotes`) an explicit `null`/empty applies as NULL/empty in M and is then validated per BR-05 (null when `M.followUpRequired = true` is missing → `400`, never a silent keep of the stored note); for non-nullable keys (`description`, `result`) `null`/wrong-type in M → `400`, and a non-boolean `followUpRequired` (including `null`) → `400 VALIDATION_ERROR` and is never treated as a flip. A **flag flip** means the body has own-property `followUpRequired` (`"followUpRequired" in body`) with a boolean value that differs from `S.followUpRequired`; T1–T4 below fire **only** on a flag flip — a body that omits the key, or sends the same value redundantly, is **not** a flip and never touches resolution state (see flip-gating rule). The server evaluates in this fixed order: (1) `401/404` auth + ticket/entry existence + belongs-to-ticket check; (2) authorization on body shape by **key presence** (see next bullet); (3) `409 VERSION_CONFLICT` on `expectedUpdatedAt` (BR-09; malformed → `400`); (4) field validation on **M** per BR-02/BR-03/BR-05 (required-when-true / prohibited-when-false re-evaluated on the merged row, with the BR-05 resolved-history exemption); (5) resolve precondition on **M + S** (requires `M.followUpRequired = true AND S.followUpResolvedAt IS NULL`, else `400`/`409` per BR-07). The resolve test therefore sees the **merged** flag, not just the stored flag — a body that flips the flag to `false` and sets `markFollowUpResolved: true` in the same call fails step (5) with `400` (see T1).
    - **Mixed-body authorization (fail-closed, key-presence rule):** if the body has an own property for **any** correctable key (`description`, `result`, `followUpRequired`, `followUpNote`, `attachmentNotes`) — decided by **key presence** (`key in body` on the parsed JSON body), **regardless of value, including `null`** (keys absent after JSON parsing, e.g. `undefined`, count as absent) — the whole request requires author-while-active-or-Administrator. In particular `{ attachmentNotes: null, markFollowUpResolved: true }` **is** a mixed body (the `null` still counts as a field edit that would clear the author's notes), so a non-author (including ticket owner) sending it gets `403 FORBIDDEN` as a whole with no partial application — they must either POST a new entry or send a fields-free resolve-only body (`{ markFollowUpResolved: true, expectedUpdatedAt? }` — no correctable key present at all), which any active staff/admin may send. `expectedUpdatedAt` and `markFollowUpResolved` are **not** correctable keys and never trigger the author requirement by themselves.
    - **`followUpRequired` flip transitions (normative; only on explicit flip):**
      - **Flip-gating rule (normative):** T1–T4 apply **only** when the PATCH body explicitly contains own-property `followUpRequired` with a value different from `S.followUpRequired`. Field-only edits (any correctable key **other than** `followUpRequired`, with the flag key absent — e.g. `{ description: "fix typo" }`) and redundant same-value sends (e.g. explicit `followUpRequired: true` on a stored `true`) are **not** flips: they leave `followUpResolvedAt`/`followUpResolvedById` untouched, never arm/re-arm the gate, and never demand a fresh `followUpNote` beyond the ordinary merged-row validity check. Concretely, `{ description: "fix typo" }` on a resolved `S: true + non-NULL` row yields `M.followUpRequired = true` by merge but fires **no** transition → `200` with resolution preserved and the ticket still unblocked.
      - **T1 — pending `true→false` (explicit flip `S: true + NULL` → `M: false`):** rejected with `400` (the pending item must be explicitly resolved first; flipping the flag does not resolve). Sending `markFollowUpResolved: true` in the **same** call does not save it — step (5) evaluates `M.followUpRequired = false` → `400`. Correct two-step path: first resolve (`M` still `true` + `markFollowUpResolved`) → `200`, then optionally flip to `false` (now T2) in a second PATCH.
      - **T2 — resolved `true→false` (explicit flip `S: true + non-NULL` → `M: false`):** allowed (author/admin only). `followUpResolvedAt`/`followUpResolvedById`/stored `followUpNote` are preserved (BR-05 exemption); client MUST omit or send empty `followUpNote` (non-empty → `400`). The gate never saw this row anyway (already non-pending).
      - **T3 — all-clear `false→true` (explicit flip `S: false + NULL` → `M: true`):** allowed (author/admin only) as a new pending: requires a fresh `followUpNote` (5–1,000 chars) supplied in the same body (the stored row has no note to reuse); `followUpResolvedAt` stays `NULL`. This arms the gate.
      - **T4 — re-arm on a resolved row (explicit flip `S: false + non-NULL` → `M: true`):** allowed (author/admin only) and **clears** `followUpResolvedAt → NULL` and `followUpResolvedById → NULL`, requiring a fresh `followUpNote` (5–1,000 chars) supplied in the same body (the stored note belongs to the prior resolved cycle and cannot be reused). This re-arms the gate as a new pending item (the old resolution stays in `updatedAt` history but the row is pending again). A resolved `S: true + non-NULL` row sent back with redundant explicit `followUpRequired: true` (no value change) is **not** T4 — it is a no-flip edit that preserves resolution (see flip-gating rule and next bullet).
      - **`followUpNote`-only edit on a resolved row (normative):** editing `followUpNote` (or `description`/`result`/`attachmentNotes`) **without** a flag flip on a resolved row (`S.followUpResolvedAt IS NOT NULL`) is an ordinary correctable-field correction (author/admin only): it **preserves** `followUpResolvedAt`/`followUpResolvedById`, does **not** re-arm the gate, and does **not** require a "fresh" note cycle. Merged-row validation still applies: if `M.followUpRequired = true`, the merged note (supplied value if the key is present, else the stored note) must be 5–1,000 chars after trim → supplying an invalid replacement note (including explicit `null`/empty when `M` is `true`) is `400`, omitting the key keeps the stored note and succeeds; if `M.followUpRequired = false`, any non-empty supplied note is `400` (client must omit/empty; stored note is retained per BR-05). Symmetric pending-row rule: editing any correctable field other than `followUpRequired` on a pending row (`S.followUpResolvedAt IS NULL`, `S.followUpRequired = true`) without a flag flip preserves the pending state (`followUpResolvedAt` stays `NULL`, gate still armed); a `followUpNote` replacement on a pending row must itself be 5–1,000 chars after trim → invalid replacement is `400`.
    - **No delete:** no DELETE endpoint exists. Deactivation of the author never removes or reattributes rows (mirrors Lab 3 BR-22).
7. **BR-07 Resolution gate (the single most important rule in Lab 4).**
   - **Precondition (normative, testable with one query):** a ticket in `OPEN`, `IN_PROGRESS`, or `WAITING_FOR_REQUESTER` **cannot** transition to `RESOLVED` while the following query returns any row:

     ```sql
     SELECT 1 FROM "ActionTaken"
     WHERE "ticketId" = :ticketId
       AND "followUpRequired" = TRUE
       AND "followUpResolvedAt" IS NULL
     LIMIT 1;
     ```

     If the query returns a row, `PATCH /api/staff/tickets/:id/status` with `{ "status": "RESOLVED" }` is rejected with **`409` + `code: "RESOLUTION_BLOCKED"`** (distinct body from the plain disallowed-transition error; see `api-spec.md`). If it returns no rows — including the case of **zero Actions Taken entries at all** — the transition proceeds subject only to the Lab 3 matrix.
    - **What "resolves" a pending follow-up:** exactly one mechanism — an explicit resolve operation (`PATCH …/actions-taken/:actionId` with `{ "markFollowUpResolved": true, "expectedUpdatedAt": … }`) on the **pending row itself**, which sets `followUpResolvedAt = getNow()` (BR-14 injectable app-code clock, passed explicitly — never the Postgres clock) and `followUpResolvedById = <authenticated actor>`. Creating a **new** Actions Taken row with `followUpRequired = false` does **not** auto-resolve older pendings. Rationale: auto-resolution ("any new row clears all flags") is ambiguous about *which* pending item was actually completed and lets a trivial new row silently unlock resolution; explicit per-row resolution is unambiguous, auditable (who/when per item), and enforceable with the single query above.
    - **Double-resolve** of an already-resolved row (`S.followUpResolvedAt IS NOT NULL`, regardless of `M.followUpRequired`) → `409` (`FOLLOW_UP_ALREADY_RESOLVED`). **Resolving a row whose merged `followUpRequired = false`** (`M.followUpRequired = false`, `S.followUpResolvedAt IS NULL`) → `400 VALIDATION_ERROR` (nothing to resolve; see BR-06 T1 — resolve first, then flip).
    - **Scope:** the gate applies to exactly the three `→ Resolved` edges (`OPEN`, `IN_PROGRESS`, `WAITING_FOR_REQUESTER`). No other edge gains a precondition. `RESOLVED → CLOSED`, reopens, cancellations, and all other transitions behave exactly as in Lab 3.
    - **Atomicity (normative locking mechanism):** under Postgres `READ COMMITTED`, a bare `EXISTS` check followed by `UPDATE`, or a bare read-`updatedAt` → compare → write, does **not** prevent a concurrent writer from committing between the check and the write. Implementations MUST therefore lock the parent ticket row in **both** gate and follow-up transactions, **and** on **every** ticket write (not only gate edges):
      ```sql
      -- first statement inside each transaction, before any gate/predicate/version check:
      SELECT 1 FROM "Ticket" WHERE id = $1 FOR UPDATE;
      ```
      (a) `PATCH /api/staff/tickets/:id/status` on **every** edge (gate or not): `BEGIN; SELECT … FOR UPDATE;` re-read the row **after** acquiring the lock, then evaluate `400` enum → `404` ticket → matrix (`409 INVALID_STATUS_TRANSITION`, Lab 3 code unchanged) → gate `EXISTS` when `status = RESOLVED` on a gate edge (`409 RESOLUTION_BLOCKED`) → `VERSION_CONFLICT` (BR-09, checked against the post-lock re-read) → `UPDATE Ticket`; `COMMIT`. (b) `PATCH /api/staff/tickets/:id/assignment` and `…/priority`: same shape — `BEGIN; SELECT parent Ticket … FOR UPDATE;` re-read → `400/404` target checks → `VERSION_CONFLICT` against the post-lock re-read → `UPDATE`; `COMMIT` (Lab 3 handlers have no transaction today — Lab 4 MUST add one; a lock-free read-compare-write is non-compliant). (c) `POST /api/staff/tickets/:id/actions-taken` and `PATCH …/actions-taken/:actionId` (create/edit/resolve): `BEGIN; SELECT parent Ticket … FOR UPDATE; SELECT the ActionTaken row … FOR UPDATE when it exists;` re-read, then insert/update; `COMMIT`. The shared row lock serializes a resolver against a concurrent follow-up flagger, so the ticket cannot end up `RESOLVED` with a pending follow-up, and serializes concurrent writers to the same ticket so a stale `expectedUpdatedAt` reliably fails. `SERIALIZABLE` isolation is **not** required; `READ COMMITTED + FOR UPDATE` with the version check **after** the lock is the specified mechanism. Compliant alternative: an atomic conditional update `UPDATE "Ticket" SET … WHERE id = $1 AND "updatedAt" = $expected` (0 rows → `409 VERSION_CONFLICT`) — but a non-atomic read-then-write without either the `FOR UPDATE` lock or the conditional `WHERE` is forbidden. `expectedUpdatedAt` alone without a lock/conditional is not a substitute (a concurrent insert has no `updatedAt` to compare against, and two concurrent PATCHes can both pass a pre-lock compare under `READ COMMITTED`).
    - **Lab 3 compatibility note:** this rule **changes** Lab 3 behavior by adding a precondition to an existing transition (Lab 3 BR-15 explicitly deferred it). The matrix shape does not change. The matrix-illegal code stays Lab 3's `INVALID_STATUS_TRANSITION` (unchanged); `RESOLUTION_BLOCKED` is a new, distinct code evaluated only after the matrix passes.
8. **BR-08 Dashboard metric definitions (normative; each is one query).** All counts are exact; `session.user.id` is the authenticated actor. "Active ticket" (staff open-set) means `status NOT IN ('RESOLVED','CLOSED','CANCELLED')`. "Mine" (requester) means `requesterUserId = session.user.id`. Times use the server clock via an **injectable app-code clock** (see BR-14); "today" means the UTC calendar day (BR-14). Every card defines its empty state and drill-down target (a queue/list filter the card links to).
    - **App-computed time bounds (normative; never SQL `now()`):** the server computes `recentlyResolvedSince = getNow() − 30 days` and `newTodaySince = startOfUtcDay(getNow())` in **application code** from the injectable clock and passes each bound as a **bound query parameter** (`$recentlyResolvedSince` / `$newTodaySince`, i.e. `WHERE "updatedAt" >= $1`). Dashboard queries MUST NOT use SQL `now()`, `CURRENT_TIMESTAMP`, `CURRENT_DATE`, or `now() - INTERVAL '30 days'` — fake timers / mocking `now()` in Node do not affect the Postgres clock, so SQL-time bounds make frozen-clock tests day-dependent and flaky (with `NOW = 2026-10-09`, T4/T5 drop out of the window on later wall-clock days). Computing the bound in app code makes freezing the JS clock sufficient and keeps the count query and its drill-down (`?updatedSince=` / `?createdSince=` with the same returned ISO string) exactly equal.
    - **Count ≡ drill-down guarantee (normative):** each card's count MUST equal its drill-down list's `meta.totalItems` when the drill-down is fetched with the documented filters. UI links MUST use exactly the documented filters (not an approximation). Tests assert this equality with a frozen clock (see `tests.md`).
    - **Lab 4 additive list filters (normative; backward-compatible, optional; invalid values → `400 VALIDATION_ERROR`):** to make exact drill-downs possible without changing Lab 3 defaults: (a) `GET /api/tickets` (Requester My Tickets) gains repeated `?status=` support (`IN` semantics — Lab 2 documented a single value; Lab 4 servers MUST accept one or repeated values) and `?updatedSince=` (ISO-8601, `updatedAt >= value`); (b) `GET /api/staff/tickets` keeps its Lab 3 repeated-`?status=` and `?ownerId=unassigned` support (confirmed per Lab 3 `api-spec.md` §3) and gains `?hasPendingFollowUp=true|false` (EXISTS pending per BR-07), `?createdSince=` (ISO-8601, `createdAt >= value`), and `?updatedSince=` (ISO-8601). These are pure additions: omitting them yields exactly Lab 3 behavior. They are listed as changed Lab 3 behavior in BR-12/`api-spec.md` solely because the accepted query surface grows.

    **Requester dashboard** (`GET /api/dashboard/requester`, role Requester only; response also returns `recentlyResolvedSince` = the exact app-computed `getNow() − 30 days` ISO bound used, so the drill-down link is exact):
    - `openTickets` = `COUNT Ticket WHERE requesterUserId = me AND status NOT IN (RESOLVED, CLOSED, CANCELLED)`. Empty: `"You have no open tickets."` Drill-down (exact): My Tickets `?status=NEW&status=OPEN&status=IN_PROGRESS&status=WAITING_FOR_REQUESTER&status=REOPENED` (enumerates the open set; equals `NOT IN` over the closed 8-enum).
    - `awaitingMyResponse` = `COUNT Ticket WHERE requesterUserId = me AND status = WAITING_FOR_REQUESTER`. Empty: `"Nothing is waiting on you."` Drill-down (exact): My Tickets `?status=WAITING_FOR_REQUESTER`.
    - `recentlyResolved` = `COUNT Ticket WHERE requesterUserId = me AND status IN (RESOLVED, CLOSED) AND updatedAt >= $recentlyResolvedSince` (app-computed bound; never SQL `now() - INTERVAL`). Empty: `"No tickets resolved in the last 30 days."` Drill-down (exact): My Tickets `?status=RESOLVED&status=CLOSED&updatedSince=<recentlyResolvedSince>` (same ISO string passed back as the list filter).
    - `totalSubmitted` = `COUNT Ticket WHERE requesterUserId = me`. Empty: `"You have not submitted any tickets yet."` (new-user state; card links to Create Ticket). Drill-down (exact): My Tickets, no filter.

    **IT Staff dashboard** (`GET /api/dashboard/staff`, roles IT Staff and Administrator; Administrator use is aggregate read-only and implies no queue/detail/status permission beyond Lab 3; response also returns `newTodaySince` = the exact start-of-UTC-day ISO bound used, so the drill-down link is exact):
    - `unassignedActive` = `COUNT Ticket WHERE ticketOwnerId IS NULL AND status NOT IN (RESOLVED, CLOSED, CANCELLED)`. Empty: `"Queue is fully assigned."` Drill-down (exact): staff queue `?ownerId=unassigned&status=NEW&status=OPEN&status=IN_PROGRESS&status=WAITING_FOR_REQUESTER&status=REOPENED`.
    - `assignedToMe` = `COUNT Ticket WHERE ticketOwnerId = session.user.id AND status NOT IN (CLOSED, CANCELLED)` (includes RESOLVED so staff see what they still need to close). Empty: `"Nothing is assigned to you."` Drill-down (exact): staff queue `?ownerId=<me>&status=NEW&status=OPEN&status=IN_PROGRESS&status=WAITING_FOR_REQUESTER&status=RESOLVED&status=REOPENED`. For Administrator callers this counts tickets owned by the calling admin (normally zero, since admins cannot be owners per Lab 3 BR-11) — the card still renders with the same empty state rather than erroring.
    - `waitingForRequester` = `COUNT Ticket WHERE status = WAITING_FOR_REQUESTER`. Empty: `"No tickets are waiting on requesters."` Drill-down (exact): staff queue `?status=WAITING_FOR_REQUESTER`.
    - `pendingFollowUp` = `COUNT DISTINCT Ticket WHERE EXISTS (pending-follow-up row per BR-07 for that ticket)`. Empty: `"No pending follow-ups."` Drill-down (exact, normative): staff queue `?hasPendingFollowUp=true` — its `meta.totalItems` equals `pendingFollowUp`. The response also includes `pendingFollowUpTicketIds` (up to 200 ids, `updatedAt desc`) as a link-construction convenience only; the 200-cap never truncates the count (clients MUST NOT build the drill-down by fetching those ids individually).
    - `resolvedPendingClose` = `COUNT Ticket WHERE status = RESOLVED`. Empty: `"Nothing is waiting to be closed."` Drill-down (exact): staff queue `?status=RESOLVED`.
    - `newToday` = `COUNT Ticket WHERE status = NEW AND createdAt >= $newTodaySince` (app-computed start-of-UTC-day bound; never SQL `now()`/`CURRENT_DATE`). Empty: `"No new tickets today."` Drill-down (exact): staff queue `?status=NEW&createdSince=<newTodaySince>` (same ISO string passed back as the list filter).
9. **BR-09 Concurrency / stale-update handling.** Optimistic locking on `Ticket.updatedAt` and `ActionTaken.updatedAt`, always combined with the BR-07 row lock:
    - Mutating endpoints (`PATCH /api/staff/tickets/:id/status`, `…/assignment`, `…/priority`, `PATCH …/actions-taken/:actionId`, including the resolve operation) accept an optional `expectedUpdatedAt` (ISO-8601 string of the `updatedAt` the client last saw).
    - If supplied and `expectedUpdatedAt !== current updatedAt` (millisecond-exact string comparison on the canonical ISO form, evaluated **after** acquiring the `FOR UPDATE` lock and re-reading the row per BR-07), the server rejects with **`409` + `code: "VERSION_CONFLICT"`** and includes `data: { currentUpdatedAt }` so the client can re-fetch without losing user input.
    - If omitted, the write proceeds (backward-compatible with Lab 3 clients) but still runs inside the same `FOR UPDATE` transaction. The UI always sends it (it always has a last-seen `updatedAt`).
    - Malformed `expectedUpdatedAt` (non-string, unparseable date, empty string) → `400 VALIDATION_ERROR` (never silently ignored). This is the single behavior; there is no "ignore-or-400" option.
    - Rationale: `updatedAt` already exists on `Ticket` (Prisma `@updatedAt`) and is added to `ActionTaken`; no ETag/version-column infrastructure is needed, and string comparison on the canonical ISO form is deterministic across the JS/Postgres boundary. Applies to Ticket status/owner/priority writes **and** Actions Taken edits/resolves alike. The `expectedUpdatedAt` compare is only a real lost-update guard when paired with the BR-07 mechanism (post-lock re-read, or equivalently an atomic `UPDATE … WHERE id = $1 AND "updatedAt" = $expected` returning 0 rows → `409`): a pre-lock read-compare-write under `READ COMMITTED` lets two concurrent PATCHes (assignment, priority, or non-gate status edges) both pass the check, so implementations MUST NOT implement BR-09 as lock-free read → compare → write on any ticket mutation. Note: `expectedUpdatedAt` guards lost-update on a single row; it does **not** substitute for the BR-07 `FOR UPDATE` lock against concurrent follow-up inserts (which have no `updatedAt` to compare).
10. **BR-10 Authorization, validation, and safe-error baseline (Lab 3 carried forward).**
    - Requester: read own tickets + own Actions Taken; create/read Public Comments on own tickets; Problem Appears Resolved on own tickets. **No** Actions Taken write, **no** Internal Notes, **no** dashboard-staff access, **no** status/assignment/priority writes.
    - IT Staff (active): full Actions Taken create/list/resolve + author-scoped edit; dashboards-staff; queue/detail/assignment/priority/status (gated by BR-07/BR-09); comments + notes. Inactive IT Staff: no authenticated access at all.
    - Administrator (active): Actions Taken create/list/**any-row edit**/resolve; **staff-dashboard aggregates read-only**; comments + notes; user management per Lab 3. Administrators do **not** gain queue/detail/assignment-target/status/priority powers and remain invalid as `ticketOwnerId` (Lab 3 BR-11/BR-16 unchanged; assignment of an Administrator or inactive user → `400`).
    - Status codes follow Lab 3 BR-24: `400` invalid input, `401` no/invalid session, `403` authenticated-but-forbidden, `404` missing-or-hidden (ownership violations stay `404`), `409` state conflicts (`RESOLUTION_BLOCKED`, `VERSION_CONFLICT`, `FOLLOW_UP_ALREADY_RESOLVED`, and the unchanged Lab 3 `INVALID_STATUS_TRANSITION` for matrix-illegal edges), `500` unexpected with `INTERNAL_ERROR` only.
    - Requester Actions Taken visibility (deliberate): `GET /api/tickets/:id/actions-taken` (own tickets only) returns the **full entry shape** — including `followUpNote` and `attachmentNotes` — because follow-up work routinely needs requester cooperation and Lab 4 defines no separate public/private flag. Staff MUST therefore write `followUpNote`/`attachmentNotes` assuming requester visibility (requester-safe wording only; genuinely internal deliberation belongs in Internal Notes, never in Actions Taken). No redaction variant exists; the shape is identical to the staff list shape.
11. **BR-11 Status enum and matrix continuity.** Ticket status remains exactly the Lab 3 8-value enum; legacy `PENDING` remains rejected with `400` everywhere. The allowed-transition matrix is byte-identical to Lab 3 `api-spec.md` §3; Lab 4 adds only the BR-07 precondition on the three `→ Resolved` edges (matrix-illegal edges keep Lab 3's `409 INVALID_STATUS_TRANSITION` code unchanged — Lab 4 does **not** rename it). The Requester Problem Appears Resolved signal (`Ticket.problemAppearsResolvedAt`) still never performs a status transition; dashboards **read** that field where relevant and never reimplement it.
12. **BR-12 Migration and regression safety.** The Lab 4 migration is strictly additive (new `ActionTaken` table + indexes + hand-written `CHECK` only; see §7). It alters, backfills, renames, or drops no Lab 1–3 table, column, index, or enum value. Changed Lab 3 behavior is limited to the explicitly listed additive items: (a) BR-07 gate precondition on three `→ Resolved` edges, (b) optional `expectedUpdatedAt` on status/assignment/priority writes, (c) additive `pendingFollowUpCount` on `GET /api/staff/tickets/:id` and status-PATCH responses, (d) additive list filters (`GET /api/tickets`: repeated `?status=`, `?updatedSince=`; `GET /api/staff/tickets`: `?hasPendingFollowUp=`, `?createdSince=`, `?updatedSince=`). Nothing else in the Lab 3 contract changes, and the matrix-illegal `409` code is unchanged, so all Lab 1–3 tests pass unmodified after the migration. Seed data is idempotent (stable identifiers) and includes Actions Taken rows exercising: zero-action tickets, all-clear tickets, and pending-follow-up tickets. Tests that assert time-dependent dashboard values MUST use fixed fixtures with a frozen clock, never wall-clock "today" (see `tests.md`).
13. **BR-13 Hardening rules.** Every Lab 4 screen: full keyboard reachability with visible focus; associated labels and `aria-describedby` errors; badge/icon meaning never carried by color alone; zero console errors or warnings in the happy path; no dead UI (disabled controls explain why); in-flight buttons disable to prevent duplicate POSTs; failed creates never clear the user's draft; every failure panel offers Retry; responsive at the three breakpoints in `ui-spec.md`.
14. **BR-14 Timezone/date-boundary rule.** The server is the sole clock, exposed as an injectable `getNow(): Date` (production default `() => new Date(Date.now())`; tests freeze it with fake timers / `Date.now` mock to `NOW`). "Today" (`newToday`) and "recent" (`recentlyResolved`) boundaries are computed in **UTC** in app code (`newTodaySince = startOfUtcDay(getNow())` = `00:00:00.000Z` of the UTC day containing `getNow()`; `recentlyResolvedSince = new Date(getNow().getTime() - 30*24*3600*1000)`) and passed as query parameters — never SQL `now()`/`CURRENT_TIMESTAMP`/`INTERVAL`. The API returns UTC ISO-8601 timestamps (`recentlyResolvedSince`, `newTodaySince` included so drill-downs reuse the exact bound); the client formats them in the viewer's locale but never computes day boundaries itself and never supplies a timezone offset. Rationale: UTC app-computed bounds are deterministic across developer machines and CI (freezing the JS clock freezes the dashboards; freezing JS alone cannot freeze the Postgres clock), need no per-request offset plumbing, and match the existing UTC-ISO convention.

## 7. Data Changes

New Prisma model `ActionTaken` (singular model name follows the `PublicComment`/`InternalNote` convention; prose and REST refer to it as "Actions Taken" / `actions-taken`):

```prisma
model ActionTaken {
  id                   Int       @id @default(autoincrement())
  ticketId             Int
  performedById        Int
  actionDate           DateTime  @default(now())   // schema default only; app MUST pass getNow() explicitly (BR-01/BR-14)
  description          String    @db.Text          // required, 5–2000 chars (BR-02)
  result               String                      // controlled vocabulary (BR-03); CHECK constraint in migration
  followUpRequired     Boolean   @default(false)   // (BR-05)
  followUpNote         String?   @db.Text          // required iff followUpRequired (BR-05)
  followUpResolvedAt   DateTime?                   // NULL = still pending (BR-07)
  followUpResolvedById Int?                        // actor that resolved (BR-07)
  attachmentNotes      String?                     // free-text pointer ≤500 chars (BR-05)
  updatedAt            DateTime  @updatedAt        // edit audit + optimistic lock (BR-06/BR-09)

  ticket       Ticket @relation(fields: [ticketId], references: [id], onDelete: Cascade, onUpdate: Cascade)
  performedBy  User   @relation(fields: [performedById], references: [id], onDelete: Restrict, onUpdate: Cascade)
  resolvedBy   User?  @relation("ActionTakenResolver", fields: [followUpResolvedById], references: [id], onDelete: SetNull, onUpdate: Cascade)

  @@index([ticketId])
  @@index([ticketId, actionDate])
  @@index([performedById])
}
```

- `User` gains back-relations `actionsTaken ActionTaken[]` and `resolvedFollowUps ActionTaken[] @relation("ActionTakenResolver")`; `Ticket` gains `actionsTaken ActionTaken[]`. No other Lab 1–3 model is touched.
- `result` values are enforced by a migration-level `CHECK (result IN (...))` plus service-layer validation (defense in depth; Prisma-native enum avoided so a future vocabulary addition stays a data migration, not an enum rewrite). Prisma schema language cannot express a `CHECK` constraint, so the migration MUST include hand-written SQL, e.g. `ALTER TABLE "ActionTaken" ADD CONSTRAINT "ActionTaken_result_check" CHECK ("result" IN ('RESOLVED_STEP','WORKAROUND','INFO_REQUESTED','ESCALATED','NO_FURTHER_ACTION'))`. Expect `prisma migrate dev` / `prisma db pull` drift warnings on this constraint (Prisma does not round-trip it) — this is accepted and MUST NOT be "fixed" by removing the constraint.
- **Response `createdAt` is an alias, not a column:** the table has `actionDate` (immutable, server-set) and `updatedAt` only. API responses expose `createdAt` as a read-only alias equal to `actionDate` (for convention consistency with comments/notes which expose `createdAt`); `createdAt` never changes and is never accepted from the client. Implementations MUST serialize `createdAt: actionDate.toISOString()` rather than adding a redundant column.
- `followUpResolvedAt`/`followUpResolvedById` are the **only** resolution-gate bookkeeping fields, and they live on `ActionTaken` — **no new column is added to `Ticket`** for the gate (the gate is a derived `EXISTS` query, BR-07). Dashboards read the existing `Ticket.problemAppearsResolvedAt` field; they do not reinvent it.
- Optimistic concurrency reuses `Ticket.updatedAt` (already present) and the new `ActionTaken.updatedAt` — no separate version column.
- Indexes mirror the `PublicComment`/`InternalNote` pattern (`[ticketId]`, `[ticketId, createdAt-equivalent]`) plus `[performedById]` for author audit queries.
- **The migration must not alter or drop any Lab 1–3 table, column, index, or enum value.** Verification: Labs 1–3 suites pass unmodified post-migration (tests.md REG rows).

## 9. Acceptance Criteria

- **AC-01** Given an active IT Staff member (owner or not) or Administrator, when they POST a valid Actions Taken entry, then the server records it with server-set `actionDate`, session-derived `performedBy`, and returns `201` with the entry shape.
- **AC-02** Given invalid Actions Taken input (blank/short/long description, unknown `result`, missing `followUpNote` when required, supplied `followUpNote` when not required, oversized `attachmentNotes`, or client-supplied `actionDate`/`performedById`/`followUpResolvedAt`/`followUpResolvedById`), when posted, then the server rejects with `400 VALIDATION_ERROR` and field errors, and no row is created.
- **AC-03** Given a Requester, when they attempt to create or edit Actions Taken (any ticket), then the server rejects with `403` and no row changes; their own ticket's list endpoint remains readable.
- **AC-04** Given a ticket in `OPEN`/`IN_PROGRESS`/`WAITING_FOR_REQUESTER` with ≥1 pending follow-up (`followUpRequired = true AND followUpResolvedAt IS NULL`), when IT Staff requests `→ Resolved`, then the server rejects with `409 RESOLUTION_BLOCKED` and the ticket status is unchanged.
- **AC-05** Given the ticket in AC-04 after every pending follow-up has been explicitly resolved per BR-07, when IT Staff requests `→ Resolved`, then the transition succeeds (`200`); and given a ticket with zero Actions Taken at all, `→ Resolved` is **not** blocked by the gate (matrix rules alone apply).
- **AC-06** Given a non-author IT Staff member (not an Administrator), when they attempt to edit another author's correctable fields (including a mixed fields+resolve body decided by key presence — even `{ attachmentNotes: null, markFollowUpResolved: true }`), then the server rejects with `403` as a whole with no partial application; the same actor **may** resolve that row's pending follow-up with a fields-free body with no correctable key present (`200` with `followUpResolvedAt`/`resolvedBy` set). Given a pending row, explicit boolean `followUpRequired true→false` without resolving first → `400` (T1) and non-boolean `followUpRequired` (incl. `null`) → `400`, never a flip; explicit flip on an already-resolved row preserves history (T2); explicit `false→true` arms/re-arms pending with a fresh supplied note (T3/T4) per BR-06; field-only edits (e.g. `{ description: "fix typo" }`) on a resolved row preserve resolution and field-only edits on a pending row preserve pending, and `followUpNote`-only corrections on a resolved row preserve resolution and never re-arm (no T fires without an explicit boolean flag flip).
- **AC-07** Given a stale `expectedUpdatedAt` on a Ticket status (any edge)/assignment/priority write or an Actions Taken edit/resolve, when submitted, then the server rejects with `409 VERSION_CONFLICT` including `currentUpdatedAt`, and no write occurs; the version compare runs after the `FOR UPDATE` lock (or via atomic conditional `UPDATE`), so concurrent stale writers cannot both succeed; retry after re-fetch succeeds.
- **AC-08** Given an assignment target that is inactive or an Administrator, when submitted, then the server rejects with `400` and ownership is unchanged (Lab 3 BR-11/BR-16 preserved).
- **AC-09** Given an authenticated Requester viewing their own ticket, when the Actions Taken area renders, then entries are visible but no create/edit/resolve controls exist or function (server `403` if forced).
- **AC-10** Given seeded data with known tickets/follow-ups and a frozen app-code clock (`getNow() = NOW`), when each dashboard endpoint is called, then every card value equals its BR-08 query result (bounds passed as app-computed params, never SQL `now()`) and equals its drill-down's `meta.totalItems` (count ≡ rows), empty states render for zero counts, and each card links to its documented exact drill-down (admin cards render without links + reason).
- **AC-11** Given any other (non-`→ Resolved`) transition, when requested, then Lab 3 matrix behavior is unchanged (gate never fires off its three edges).
- **AC-12** Given the full Labs 1–3 suite run after the Lab 4 migration, when executed, then all prior tests pass unmodified and no Lab 1–3 row was altered or lost.
- **AC-13** Given each Lab 4 screen at desktop/tablet/mobile widths with keyboard only, when exercised, then content is reachable with visible focus, labeled controls, no clipping/overflow, no console errors, no dead UI, duplicate clicks create exactly one row, and failures preserve input with a Retry path.

## 11. Assumptions and Decisions

1. **Action Date/Time is server-set, never client-supplied** (BR-01) — prevents backdating; matches comment/note `createdAt` conventions.
2. **Description required, 5–2,000 chars** (BR-02) — floor rejects junk, ceiling reuses the comment/note counter UI.
3. **Result is a controlled 5-value vocabulary, not free text** (BR-03) — queryable, validatable, keeps narrative in `description`.
4. **Performed-by is always the session actor** (BR-04) — mirrors Lab 3 BR-03; no client identity input.
5. **Follow-up Note required-when-true and rejected-when-false** (BR-05) — strict rejection over silent ignore so no typed intent silently vanishes.
6. **Attachment Notes is a ≤500-char free-text pointer, not an upload** (BR-05) — Lab 4 adds no file-upload scope.
7. **Any active IT Staff (or Administrator) may author on any ticket; ownership ≠ authorship** (BR-06) — adopts the handout's "different IT Staff member" sentence literally.
8. **Actions Taken are editable (not append-only), author-or-Administrator for correctable fields, any-staff for follow-up resolution, no delete** (BR-06) — operational records need correction; accountability preserved by restricting rewrites while letting any staffer complete follow-up work.
9. **Resolution gate = single `EXISTS (followUpRequired AND followUpResolvedAt IS NULL)` query; only explicit per-row resolve clears it; new rows never auto-clear; zero rows never block; `409 RESOLUTION_BLOCKED`** (BR-07) — unambiguous, auditable, one-query enforceable, serialized by `SELECT … FOR UPDATE` on the parent Ticket in the status transaction (every edge) and all Actions Taken transactions (not by `expectedUpdatedAt` alone); flag flips T1–T4 fire only on explicit `followUpRequired` key so field-only edits never re-arm.
10. **Concurrency = optional `expectedUpdatedAt` → `409 VERSION_CONFLICT` with `currentUpdatedAt`, on every Ticket write (all status edges + assignment + priority, each in a `FOR UPDATE` transaction with post-lock compare or atomic conditional `UPDATE`) and Actions Taken edits/resolves alike; malformed → `400`** (BR-09) — reuses existing `updatedAt`, no new version infrastructure, backward-compatible when omitted, and a real lost-update guard (never lock-free read-compare-write).
11. **Dashboard metrics are exact COUNT queries with app-computed UTC bounds passed as parameters (never SQL `now()`), defined empty states, and exact drill-down targets with count ≡ rows** (BR-08, BR-14) — no vague "open" or "recent"; injectable app clock keeps server and CI deterministic under fake timers; additive list filters make every drill-down exact.
12. **No new `Ticket` column for the gate; `problemAppearsResolvedAt` is read, not reinvented; migration is strictly additive plus hand-written `CHECK`; response `createdAt` is an alias of `actionDate`** (Data Changes, BR-11/BR-12) — zero-touch on Labs 1–3 tables; Prisma drift on the `CHECK` is expected.
13. **Administrator reuses the staff dashboard endpoint as aggregate read-only without drill-down links (disabled with reason), and holds Actions Taken edit/resolve powers API-only with no Staff Detail UI surface; gains no queue/detail/status powers and stays an invalid owner** (BR-08/BR-10, `ui-spec.md` §2.2–§2.3) — per handout §4.6 and Lab 3 BR-11/BR-16; this avoids dead UI per BR-13.
